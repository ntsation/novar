This is the documentation of the development version (the main branch). It can describe things that are not released yet.

Syntax stability

A program that works today keeps working. The syntax is grouped in editions. The only edition so far is 2026, and its syntax is frozen: from the release that contains this page, a program written in edition 2026 is accepted by every later Telvax that reads edition 2026.

What is promised

Section titled “What is promised”
  • Programs are not broken. Every program in tests/editions/2026/ must keep passing telvax check, telvax fmt --check and, when it has test_... functions, telvax test. The test that runs them is cli/tests/editions.rs.
  • The files are frozen. tests/editions/2026/CHECKSUMS holds a hash of each program. Changing a program, or adding one without its line, fails the test. A pull request that has to edit a frozen program is a breaking change and needs a new edition (below).
  • New syntax may be added. A new word, form or standard library function that makes no old program stop working is an ordinary feat: change. New programs go into the frozen directory too, so the promise grows.
  • Error messages are not part of it. The text of a diagnostic, the lint warnings and the output of telvax fmt for code the formatter used to reject may change. The formatter does not change the layout of a program that is already formatted.

What is not promised

Section titled “What is not promised”
  • The std library can gain functions, and a function can get a new overload. Removing or changing one follows the same rule as syntax: a new edition.
  • The native backend, GPU execution and the accelerator outputs are listed in docs/design/status.md; what runs there can grow, and a program that did not compile natively may.
  • A bug fix may reject a program that only worked because of the bug (a type error the checker missed). The change says so in CHANGELOG.md.

Choosing an edition

Section titled “Choosing an edition”

telvax.toml names the edition of a package:

  • Without the line, the package is read as the newest edition the compiler knows. tvpm new writes it, so a new package is pinned from the start.
  • An edition the compiler does not know is an error that lists the ones it does and says to update Telvax if the package is newer.
  • A single file with no telvax.toml is read as the newest edition.

A new edition

Section titled “A new edition”

A change that makes an old program stop compiling, or changes what it means, goes in a new edition and not in the existing one:

  1. The old edition keeps compiling as it did. The compiler reads both, chosen by edition.
  2. The new directory tests/editions/<year>/ gets its own frozen programs and CHECKSUMS, and the year is added to EDITIONS in tools/package-manager/src/manifest.rs.
  3. CHANGELOG.md lists what changed, and telvax-migrate (tools/migrate) gets a rule that rewrites old source to the new edition where that can be done mechanically.
  4. How long an old edition stays supported is decided when the second edition is proposed; dropping one is a feat!: change of its own.

What exists today

Section titled “What exists today”

Done: the edition line and its check, the frozen programs and the test that guards them, and this page. Not done yet: a second edition (so reading two editions is untested), warnings for deprecated forms, and a telvax migrate command inside the telvax binary. The telvax-migrate tool converts the old Rust-style syntax and is still a separate program that will be removed.
